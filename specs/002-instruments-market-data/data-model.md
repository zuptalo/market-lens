# Data Model: Instruments and Daily Market Data

Identifiers are UUIDs generated by the application unless noted; reference-data
migrations use stable literal UUIDs. Event timestamps are
UTC `timestamptz`; financial sessions are exchange-local `date`; prices use
`numeric(20,8)`. Schema and reference-data changes are forward migrations.

## Exchange

Fields: `id`, unique immutable ISO 10383 `mic`, required name, ISO country/currency,
IANA `timezone`, active, and audit timestamps. Has instruments and sessions.

## ExchangeSession

Composite key `(exchange_id, session_date)`; status `open`, `half_day`, or `closed`;
UTC `opens_at`/`closes_at` required for trading sessions; official `source_reference`.
Close follows open and both map back to the local session date. Open/half-day rows drive
gap detection; closed rows need no bar.

## Instrument

Fields: stable `id`, exchange, ISIN, ticker, name, ISO currency/country, type (initially
`common_stock`), optional sector/industry, active, `purchasability_status`
(`user_confirmed`, `unverified`, `unavailable`), and audit timestamps.

Constraints: unique `(exchange_id, ticker)` among current listings and unique
`(exchange_id, isin)` where ISIN exists. ISIN is not globally unique because one security
may have multiple listings. Rename/status changes preserve the internal ID.

## ProviderInstrument

Maps provider identity to domain identity: `provider`, `provider_symbol`, instrument,
active, timestamps. Primary key `(provider, provider_symbol)` and one active mapping per
instrument/provider.

## ResearchUniverse and UniverseMembership

`ResearchUniverse`: ID, stable code, name, description, active, timestamps.
`UniverseMembership`: universe/instrument, inclusion date range, curation source/note,
timestamps. Ranges for a pair cannot overlap. Migration creates `nordic-liquid-v1`; UI
editing is outside this feature. Its initial 100 listings are 25 user-reviewed current
large-cap benchmark constituents per primary Nordic exchange, with selection date/source
recorded by the migration.

## ImportRun and ImportItem

`ImportRun` stores ID, kind (`universe_sync`, `backfill`, `daily_update`, `retry`),
provider, inclusive requested dates, status, optional parent run, timing, non-negative
counts, sanitized error code/summary, and application version. State:
`queued → running → succeeded | partial | failed | cancelled`; terminal rows are immutable.

`ImportItem` stores one run/instrument scope, requested dates, status, counts, attempts,
timing, and safe error. `(run_id, instrument_id)` is unique. Failed items define retry
scope exactly.

## DailyPriceBar and PriceBarRevision

Current daily bar key: `(instrument_id, session_date)`. Required positive open/high/low/
close, non-negative bigint volume, optional positive adjusted close, currency, provider,
canonical `source_hash`, import run, and first/last observation timestamps. Enforce
`low ≤ open/close ≤ high`.

An identical hash causes no write. A changed valid hash is copied to append-only
`PriceBarRevision` with revision number, superseding run/time, then updates current data
in the same transaction. Revisions are unique by instrument/session/revision.

## CorporateAction

Fields: ID, instrument, provider/action identity, type (`split`, `reverse_split`,
`dividend`, `symbol_change`, `delisting`), ex/effective session, optional ratio/amount/
currency/old-new symbol, source hash, import run, and observation timestamps. Provider
action identity is unique; corrections are explicit, never silent.

## DataQualityFinding

Fields: ID, instrument, optional session, run/item, rule, severity (`warning`, `error`),
disposition (`flagged`, `rejected`), safe detail, status (`open`, `resolved`,
`accepted_limitation`), timestamps, and resolving run.

Required rules: duplicate/out-of-order source row, invalid OHLC, non-positive price,
negative/zero volume, missing session, provider gap, suspicious jump, and possible
corporate-action discontinuity. Findings never invent/interpolate data.

## Indexes

- Instrument normalized ticker/name search, ISIN, exchange/country/currency/status.
- Bars `(instrument_id, session_date DESC)` and `(session_date, instrument_id)`.
- Runs `(started_at DESC)` and status.
- Findings `(status, severity, session_date DESC)` and instrument.
- Membership by universe/effective date.

## Transaction Boundaries

- Each instrument/date item commits independently; one failure yields a partial run.
- Validation finishes before current-bar mutation.
- Revision, current update, findings, and counters share one transaction.
- Advisory locks prevent overlapping provider/instrument/interval mutation.
- Terminal run totals are derived from item rows.
