# Feature Specification: Self-Provisioned Signing Key

**Feature Branch**: `009-self-provisioned-keys`

**Created**: 2026-08-31

**Status**: planned
<!-- Market Lens spec lifecycle: planned → in-progress → in-review → shipped. -->

**Input**: The operator should supply only the database connection. Anything the application
can generate for itself should be generated on first start and kept with the data, so that
backing up and moving an installation is one artifact rather than several coupled ones.

## Why this exists

Deploying Market Lens today requires three coupled values: `DATABASE_URL`, `AUTH_SECRET`,
and `EXTERNAL_CREDENTIAL_KEY` with its version. Two of them are generated by the installer
and then have to be carried around by hand, and losing track of them fails in ways that are
easy to miss and hard to undo:

- Restore the database on a new host without the same `AUTH_SECRET` and everybody is
  silently signed out, with no error explaining why.
- Restore it without the same `EXTERNAL_CREDENTIAL_KEY` and the stored provider credentials
  are **permanently unreadable**. The only remedy is to redo setup.

This already happened once: a deployment updated to a release that requires `AUTH_SECRET`
crashed on start with `AUTH_SECRET is required in production`, because the environment
predated the setting.

## The boundary this feature draws

The two keys look interchangeable — both are random, both are generated by the installer —
but they protect different things, and that difference decides where each may live.

`AUTH_SECRET` signs session tokens, CSRF tokens, emailed capabilities, and login codes. What
it protects is **rows in the database it would be stored in**. A stolen backup containing
both gives an attacker digests plus the key that made them, and still no way in: a session
is only usable if a matching row exists in the *live* database, which a backup does not
grant. Moving it into the database costs little and removes the silent-sign-out failure.

`EXTERNAL_CREDENTIAL_KEY` encrypts the EODHD API key and the SMTP password **inside** that
same database. Storing it there would mean the lock and its key travel in the same file. A
leaked backup would yield working provider credentials in plaintext instead of ciphertext.
Backups are the most likely way a self-hosted database ever escapes, so this key must stay
outside the data it protects.

**Therefore**: `AUTH_SECRET` becomes self-provisioned and database-resident.
`EXTERNAL_CREDENTIAL_KEY` remains external, and this specification improves how it is
handled rather than moving it.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Deploy with only a database connection (Priority: P1)

Someone deploying Market Lens supplies `DATABASE_URL` and nothing else. On first start the
application provisions its own signing key, records it, and runs. Starting again reuses the
same key rather than minting a new one, so sessions issued before a restart keep working.

**Why this priority**: It is the whole point of the feature and it removes the failure that
took production down.

**Independent Test**: Start against an empty database with only `DATABASE_URL` set, confirm
it becomes healthy, sign in, restart the process, and confirm the session still works.

**Acceptance Scenarios**:

1. **Given** an empty database and only `DATABASE_URL`, **When** the application starts,
   **Then** it provisions a signing key, becomes healthy, and reports no missing
   configuration.
2. **Given** an application that has already provisioned its key, **When** it restarts,
   **Then** it reuses the stored key and every unexpired session remains valid.
3. **Given** several instances starting against one database at the same instant, **When**
   they provision, **Then** exactly one key exists and every instance uses it.
4. **Given** a database restored onto a different host, **When** the application starts,
   **Then** sessions issued before the restore still work, because the key travelled with
   the data.
5. **Given** an explicitly supplied `AUTH_SECRET`, **When** the application starts, **Then**
   the supplied value is used and no key is provisioned, so an existing deployment is not
   silently re-keyed.

---

### User Story 2 - Rotate the signing key deliberately (Priority: P2)

The owner can replace the signing key from the host when they have reason to believe it is
compromised. Rotation signs everybody out, which is the intended effect, and says so before
it happens.

**Why this priority**: A key that can never be changed is a key that cannot be recovered
from. It follows Story 1 because provisioning has to exist first.

**Independent Test**: Sign in, rotate the key from the host, and confirm the existing
session is refused and a fresh sign-in succeeds.

**Acceptance Scenarios**:

1. **Given** an active session, **When** the owner rotates the signing key, **Then** that
   session is refused afterwards and the command says every session was ended.
2. **Given** a rotation, **When** it is performed, **Then** it is recorded in the audit
   trail without recording the key itself.
3. **Given** a rotation that fails part way, **When** it is retried, **Then** the
   installation is left on exactly one usable key, never between two.

---

### User Story 3 - Be told what is missing before it breaks (Priority: P2)

An operator who has not supplied `EXTERNAL_CREDENTIAL_KEY` is told at start, in one message
that names the value and what it protects, rather than discovering it when a start fails or
when a restore silently loses their provider credentials.

**Why this priority**: The remaining external value is now the only one an operator can get
wrong, so the cost of getting it wrong must be visible.

**Independent Test**: Start without the credential key and confirm the message names the
value, says what becomes unreadable without it, and tells the operator to keep it with
their backups.

**Acceptance Scenarios**:

1. **Given** no `EXTERNAL_CREDENTIAL_KEY` and no stored provider credentials, **When** the
   application starts, **Then** it starts and warns that provider credentials cannot be
   stored until one is supplied.
2. **Given** stored provider credentials and a missing or wrong key, **When** the
   application starts, **Then** it refuses to start and names the value it needs, without
   revealing anything about the stored ciphertext.
3. **Given** a running installation, **When** the owner asks for its configuration state,
   **Then** they are told which values are self-provisioned and which they must retain,
   with no secret in the output.

---

### Edge Cases

- Two instances start against an empty database simultaneously: exactly one key is
  provisioned, and the loser adopts it rather than failing.
- The database is unreachable at first start: the application fails to become ready and
  provisions nothing, so a later start is not left with a half-written key.
- An operator supplies `AUTH_SECRET` after the application has already provisioned one: the
  mismatch is reported rather than silently signing everybody out.
- An operator removes a previously supplied `AUTH_SECRET`: the application must not quietly
  provision a different one and sign everybody out; it reports the change.
- A database is restored from a backup taken before the key existed: provisioning happens
  once on that start, and the operator is told sessions were reset.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The application MUST require only `DATABASE_URL` to start against an empty
  database in production.
- **FR-002**: The application MUST provision a signing key of at least the current strength
  on first start when none exists, using a cryptographically secure source.
- **FR-003**: Provisioning MUST be atomic and safe under concurrent start: exactly one key
  results, and every instance uses it.
- **FR-004**: The application MUST reuse a stored key on every subsequent start.
- **FR-005**: An explicitly supplied `AUTH_SECRET` MUST take precedence, and a supplied
  value that disagrees with a stored one MUST be reported rather than silently resolved.
- **FR-006**: The stored key MUST never appear in logs, errors, API responses, events, audit
  entries, or command output.
- **FR-007**: The owner MUST be able to rotate the signing key from the host, in one
  transaction, ending every session, recorded in the audit trail without the key.
- **FR-008**: `EXTERNAL_CREDENTIAL_KEY` MUST remain external to the database, and the
  application MUST refuse to start when stored provider credentials exist and it is missing
  or wrong.
- **FR-009**: The application MUST report, at start and on request, which configuration
  values it provisioned for itself and which the operator must retain, naming no secret.
- **FR-010**: An installation whose database is restored elsewhere MUST keep working
  sessions without the operator carrying anything beyond the database and the credential key.

### Test-First Proof *(mandatory)*

- **Initial failing test**: A configuration test asserting that a production start with only
  `DATABASE_URL` succeeds. It must fail because loading currently returns
  `AUTH_SECRET is required in production`.
- **Expected red reason**: The returned error names the missing value — a behavioral
  assertion on the load result, not a compilation or fixture failure.
- **Green evidence**: The configuration, auth, and command suites, plus a concurrency test
  for simultaneous provisioning and an integration test proving sessions survive a restart.
- **Database migration proof**: Required. The key is stored, so an ordered migration must
  create it, and a migration test must prove both a clean install and an upgrade from the
  current schema without any manual step.

### Responsive UI Behavior *(mandatory for user-facing features; otherwise state N/A)*

N/A. This feature has no user-facing surface. Configuration state reported to the owner
reuses the existing integration-status view and adds no new screen.

### Live Update Behavior *(mandatory for client-visible data; otherwise state N/A)*

Rotating the signing key ends every session, which the existing session-revocation events
already report to the devices affected. No new event type is introduced.

### Identity, Ownership, and Permissions *(mandatory for user/account data; otherwise state N/A)*

- **Bootstrap and invitations**: Unchanged. This feature alters how the key that signs
  session material is obtained, not who may create or hold an account.
- **Ownership and authorization**: The stored key is instance configuration, not user data.
  Reading or rotating it requires host access, not merely an owner session, because an owner
  session is itself derived from it.
- **Security evidence**: Tests proving the key never appears in any output; that a rotation
  ends every session; that concurrent provisioning yields one key; and that the credential
  key is still required whenever encrypted provider credentials exist.

### PWA and Notification Behavior *(mandatory when applicable; otherwise state N/A)*

N/A.

### Key Entities *(include if feature involves data)*

- **Instance signing key**: The self-provisioned secret used to derive session, CSRF,
  capability, and login-code digests. One per installation, created once, replaceable only
  by explicit rotation, and never emitted.

## Success Criteria *(mandatory)*

- **SC-001**: A production deployment starts successfully against an empty database with
  `DATABASE_URL` as its only required setting.
- **SC-002**: Restoring the database onto a different host preserves every unexpired session
  without the operator carrying any additional value.
- **SC-003**: 100 instances starting simultaneously against one empty database produce
  exactly one signing key.
- **SC-004**: No signing key appears in any log line, error, response, event, audit entry, or
  command output, verified by a scan over a complete lifecycle.
- **SC-005**: Rotating the key ends every existing session and permits immediate sign-in.
- **SC-006**: An installation with stored provider credentials refuses to start without the
  correct credential key, and the refusal names what is needed without describing what is
  stored.
- **SC-007**: The number of values an operator must supply to deploy falls from three to
  one, and the number they must retain to restore falls from three to two.

## Assumptions

- The signing key protects only material whose rows live in the same database, so storing it
  there does not weaken it against a stolen backup: a session is usable only against the
  live database. This is the reasoning that makes the feature safe, and it is why the
  credential key is deliberately excluded from it.
- Existing deployments that already supply `AUTH_SECRET` continue to work unchanged. Their
  supplied value wins, and no upgrade re-keys an installation.
- The credential key may later move to a file rather than an environment variable to make it
  easier to carry, but it does not move into the database. That is a separate decision and
  out of scope here.
- The installer stops generating `AUTH_SECRET` once this ships, but must not remove one from
  an existing secret, because doing so would sign everybody out.
